## 1. Who started a generator

**Every place a start can come from:**

| Source | How | Origin recorded |
|---|---|---|
| Voltage loop, MEP and Kubota (`check_auto_generator`) | `start_generator` | `auto` |
| `/setgen?state=1`: dashboard button and Alexa's start intent | `start_generator` | `manual` |
| `/writereg` to 0x004D by hand | Raw write | None: stays `manual` |
| The AGS panel | The AGS itself | None: stays `manual` |
| The AGS's own exercise or low-voltage start | The AGS itself | None needed: it has its own reason |

**Pi5.** `/data` now has `mep803aStartOrigin`, `kubotaStartOrigin`, and `…StartOriginAt` beside them. The first origin wins, so pressing start during an automatic run leaves it automatic. It clears by following the AGS's Action rather than `stop_generator()`, because a run can also end by `/setgen`, a fault or the AGS itself. A failed read clears nothing, and a start that never ran is forgotten after `GEN_START_TIMEOUT_S`. The diff changes four existing lines (the signature and the three callers) and adds no Modbus calls.

**Agent.** Samples and `gen_runs` gain the origin. `manual_on` with origin `auto` goes through the existing threshold check, so it becomes `agent` or `auto`. Origin `manual`, or none, stays `manual`; exercise and other reasons are untouched.

**A dashboard restart during a run loses the origin**, which is in memory. The agent keeps the first origin it saw for that run. If the restart came before any sample had one, the run stays `manual`.

## `/autogen`: investigation only, nothing changed

**What the intents expect.** `EnableAutoGenIntent` and `DisableAutoGenIntent` call `set_autogen()` in `vps/alexa_solar.py`:

1. `GET http://10.8.0.2:8080/autogen?enable=1` (or `0`), expecting 200.
2. After 0.5 s, `GET /autogen`, expecting the plain text `ON` or `OFF`, and compare it with what was asked.

`get_autogen_status()` also reads `GET /autogen`, but nothing calls it.

**What the Pi5 offers.** There's no `/autogen` route; from the VPS it returns **404**. I checked that with a plain read, without sending either intent. So both intents always say "Failed to enable auto control. Current state: unknown", and change nothing. The same control exists elsewhere:

- `GET /config?autoGenEnabled=1|0` sets it and saves it. This is what the dashboard's toggle uses, and it answers 200 from the VPS.
- `/data` publishes `autoGenEnabled` as true or false.

**Proposal: change only the VPS, about 6 lines.** Point `set_autogen()` at `/config?autoGenEnabled=1|0`, verify from `/data`'s `autoGenEnabled`, and map that to `ON`/`OFF` for the existing speech. No new Pi5 endpoint, no dashboard restart, and only an `alexa-solar` restart.

**A decision for you first.** Today these intents fail harmlessly. Fixing them means a voice command can turn off automatic generator starts, and Alexa can mishear. With auto control off, the Pi5's voltage loop won't start a generator however low the pack gets, and its "Battery Low" Telegram alert won't fire either, because that alert sits in the same function, after the early return. I didn't check whether the AGS's own settings would start one. If you want it, one option is to fix enable only and leave disable failing, or have disable ask for confirmation. **Nothing has been changed.**
